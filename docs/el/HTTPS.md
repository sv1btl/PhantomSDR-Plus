# Ασφαλής πρόσβαση — https://

Ένας σταθμός PhantomSDR-Plus μπορεί να είναι προσβάσιμος μέσω **https://** εκτός από το http://. Ο browser δείχνει τότε το λουκέτο, η σύνδεση είναι κρυπτογραφημένη, και οι browsers επιτρέπουν στη σελίδα τον καλύτερο δρόμο ήχου τους (το AudioWorklet), που τον στερούν από τις απλές σελίδες http. Η διεύθυνση http συνεχίζει να λειτουργεί ακριβώς όπως πριν, δίπλα-δίπλα.

Αυτό το κάνει ο **Caddy**, ένας μικρός web server που μπαίνει μπροστά από τον δέκτη στη θύρα 443. Ο Caddy παίρνει δωρεάν πιστοποιητικό από το **Let's Encrypt** για το όνομα DNS του σταθμού σας και το ανανεώνει μόνος του, κάθε δυο-τρεις μήνες, χωρίς να χρειάζεται να κάνετε τίποτα.

---

## Τι χρειάζεστε

| | |
|---|---|
| **Ένα όνομα DNS** | Το Let's Encrypt πιστοποιεί ονόματα, όχι σκέτες διευθύνσεις IP. Ένα δωρεάν όνομα dynamic DNS (no-ip, DuckDNS, dynu κ.ά.) που δείχνει στη δημόσια διεύθυνσή σας αρκεί, και η διεύθυνση μπορεί να αλλάζει — το όνομα την ακολουθεί. |
| **Δύο ακόμη θύρες στο router** | Προωθήστε τις TCP **443** (https) και TCP **80** στον υπολογιστή του δέκτη, μαζί με τη δημόσια θύρα σας (9000). Η θύρα 80 χρησιμοποιείται μόνο για να αποδειχθεί στο Let's Encrypt ότι το όνομα είναι δικό σας, όταν εκδίδεται και ανανεώνεται το πιστοποιητικό. |
| **Σταθμό στημένο με τις ερωτήσεις του σταθμού** | Πρέπει να υπάρχει το `station.conf`. Σε σταθμό που εγκαταστάθηκε πριν από τις ερωτήσεις του σταθμού, τρέξτε πρώτα μία φορά `bash configure-station.sh` — προτείνει τις θύρες που ο σταθμός σας ήδη χρησιμοποιεί, οπότε τίποτα δεν μετακινείται. |

---

## Ενεργοποίηση

### Κατά την εγκατάσταση

Στις ερωτήσεις του σταθμού, στην ομάδα **Internet**, απαντήστε ναι στο:

```
  Also serve the receiver over https://? [y/N]: y
```

Το πρόγραμμα εγκατάστασης εγκαθιστά τον Caddy, παίρνει το πιστοποιητικό και στο τέλος δείχνει και τις δύο διευθύνσεις.

### Σε σταθμό που ήδη λειτουργεί

```bash
cd ~/PhantomSDR-Plus
bash setup-https.sh
```

Διαβάζει το όνομα DNS από το `station.conf`, εγκαθιστά τον Caddy (από τη διανομή σας· στο Ubuntu 22.04 από το αποθετήριο του ίδιου του Caddy), τον κατευθύνει στον δέκτη, ξαναφτιάχνει τη σελίδα ώστε να δείχνει τη διεύθυνση https, επανεκκινεί το proxy και περιμένει το πιστοποιητικό. Το ναι στην ερώτηση https του `bash configure-station.sh` κάνει ακριβώς το ίδιο.

Όταν τελειώσει:

```
  ✔ https://myname.ddns.net/ is live

  https://myname.ddns.net/   — and http://myname.ddns.net:9000/ as before
```

### Έλεγχος και απενεργοποίηση

```bash
bash setup-https.sh --status    # είναι ενεργό, και απαντά το πιστοποιητικό;
bash setup-https.sh --remove    # κλείνει το https· το http μένει ακριβώς όπως είναι
```

Το admin panel δείχνει το ίδιο στις **Ρυθμίσεις → HTTPS**: **🔍 CHECK** σε σταθμό με https, και σε σταθμό μόνο με http **🔒 SET UP HTTPS**, που ελέγχει ό,τι μπορεί και δίνει τις παραπάνω εντολές για αντιγραφή σε τερματικό. Δείτε [Admin Panel](ADMIN_PANEL_SETUP.md).

Αν αλλάξετε αργότερα το όνομα DNS με το `bash configure-station.sh`, ο Caddy μεταφέρεται μόνος του στο νέο όνομα.

## Πώς λειτουργεί

```
  visitor ──https──► Caddy :443 ──► proxy.py :9014 (this computer only) ──► spectrumserver, panel, RADE …
  visitor ──http───────────────────► proxy.py :9000 ───────────────────────► the same
```

| Θύρα | Τι | Ανοιχτή στο router |
|---|---|---|
| 443 | Caddy — https | ναι |
| 80 | Caddy — ο έλεγχος του πιστοποιητικού, και ανακατεύθυνση σε https | ναι |
| 9000 | proxy.py — http, όπως πριν | ναι |
| 9014 | proxy.py — εκεί παραδίδει ο Caddy τους επισκέπτες | όχι — μέσα στον υπολογιστή |

Ο Caddy φτάνει στο proxy από δική του θύρα, γιατί, από τη μεριά του proxy, κάθε επισκέπτης που έρχεται μέσω Caddy θα φαινόταν αλλιώς να έρχεται από τον ίδιο τον υπολογιστή — και ένα αίτημα από τον ίδιο τον υπολογιστή θεωρείται έμπιστο: μπορεί να αποσυνδέει ακροατές και δεν μετρά στα όρια ανά IP. Στη θύρα 9014 το proxy παίρνει από τον Caddy την πραγματική διεύθυνση του επισκέπτη και δεν θεωρεί ποτέ έναν επισκέπτη τοπικό, οπότε η λίστα ακροατών, τα όρια ανά IP και το kick του sysop λειτουργούν ακριβώς όπως μέσω http, και κανείς δεν μπορεί να κάνει kick σε ακροατή μέσω https.

## Τι αλλάζει για τους ακροατές

- **Λειτουργούν και οι δύο διευθύνσεις.** Οι κατάλογοι και ο χάρτης του websdr.org συνεχίζουν να δείχνουν τη διεύθυνση http· η κλήση επιστροφής του websdr.org και οι πελάτες Kiwi χρησιμοποιούν http.
- **Καλύτερος ήχος μέσω https.** Οι browsers δίνουν σε μια ασφαλή σελίδα το AudioWorklet, πιο σταθερό δρόμο ήχου από αυτόν που αναγκάζονται να χρησιμοποιούν οι απλές σελίδες http.
- **Receive Diversity με σταθμούς μόνο http.** Ένας browser δεν επιτρέπει σε σελίδα https να ανοίξει απλές συνδέσεις `ws://`, και οι περισσότεροι σταθμοί PhantomSDR+ και κάθε KiwiSDR δεν προσφέρουν τίποτε άλλο. Από τη σελίδα https γίνονται λοιπόν προσβάσιμοι μέσω του relay diversity του σταθμού — δείτε *Receive Diversity μέσω https* παρακάτω. Συνεργάτες που έχουν οι ίδιοι https, και τα UberSDR, συνδέονται απευθείας.
- **Έλεγχος πομποδέκτη (TCI-CAT).** Οι συνδέσεις στο `127.0.0.1` του υπολογιστή του ίδιου του ακροατή επιτρέπονται από σελίδα https στους σημερινούς Chrome, Edge και Firefox. Η σελίδα συνδέεται μόνο όταν ο ακροατής ανοίξει το **TCI-CAT** ή ενεργοποιήσει το **CAT Sync**· τότε ο Chrome και ο Edge ζητούν μία φορά άδεια πρόσβασης σε προγράμματα και συσκευές του υπολογιστή ή του δικτύου του ακροατή. Η άρνηση απενεργοποιεί μόνο το TCI-CAT.

## Receive Diversity μέσω https

Μια σελίδα https φτάνει σε συνεργάτες diversity που έχουν μόνο http — τους περισσότερους σταθμούς PhantomSDR+, κάθε KiwiSDR — μέσω του δικού του relay του σταθμού, του `websdr_relay.py`, του ίδιου που εξυπηρετεί τους συνεργάτες WebSDR. Ο browser συνδέεται με ασφάλεια στο `wss://myname.ddns.net/relay/…` και το relay συνεχίζει μέσω `ws://`. Το panel το κάνει μόνο του. Το relay μεταφέρει μόνο ήχο diversity (PhantomSDR+ `/audio`, KiwiSDR `/kiwi/…/SND`), συνδέεται μόνο σε δημόσιες διευθύνσεις και κρατά τα συνηθισμένα όριά του. Αν δεν τρέχει, μια σελίδα https φτάνει μόνο σε συνεργάτες που έχουν οι ίδιοι https.

Σε σταθμό με https, λοιπόν, κρατήστε το relay ενεργό:

- **Ενεργοποίηση https με τις ερωτήσεις του σταθμού:** μόλις ενεργοποιηθεί το https, η ερώτηση για το relay που ακολουθεί προτείνει «ναι» — κρατήστε το, και εγκαθίσταται και ξεκινά και το relay. Το `bash setup-https.sh` μόνο του δεν το εγκαθιστά.
- **Σταθμός που ήδη τρέχει https:** ελέγξτε με `systemctl is-active phantomsdr-websdr-relay`. Αν δεν είναι ενεργό, τρέξτε `bash setup_websdr_relay.sh`, ή `bash configure-station.sh` και απαντήστε «ναι» στην ερώτηση για το relay. Πίσω από το proxy δεν χρειάζεται θύρα στο router ούτε νέο build.
- **Έλεγχος:** το `https://myname.ddns.net/relay/status` απαντά με μερικές γραμμές που αρχίζουν με `"service": "PhantomSDR-Plus WebSDR relay"`.

Μέσω του relay ο συνεργάτης βλέπει τη διεύθυνση του σταθμού σας, όχι του ακροατή· ένας συνεργάτης με όριο ανά IP μετρά λοιπόν όλους τους ακροατές σας που περνούν από το relay μαζί. Ένας σταθμός μόνο με http δεν χρειάζεται τίποτε από αυτά: μια σελίδα http ανοίγει συνδέσεις `ws://` και `wss://` απευθείας.

## Μόνο για το τοπικό δίκτυο — `--lan`

Χωρίς όνομα DNS, το https μπορεί να χρησιμοποιηθεί μέσα στο σπίτι:

```bash
bash setup-https.sh --lan
```

Ο Caddy εκδίδει τότε δικό του πιστοποιητικό για την τοπική διεύθυνση και το όνομα του υπολογιστή. Οι browsers δεν γνωρίζουν αυτό το πιστοποιητικό και προειδοποιούν την πρώτη φορά· αποδεχτείτε το, ή κάντε τους υπολογιστές που χρησιμοποιείτε να εμπιστεύονται το root πιστοποιητικό του Caddy:

- στον ίδιο τον υπολογιστή του δέκτη: `sudo caddy trust`
- σε άλλον υπολογιστή: αντιγράψτε το `/var/lib/caddy/.local/share/caddy/pki/authorities/local/root.crt` από τον δέκτη (την ακριβή διαδρομή τη δείχνει το `sudo caddy environ`, στο `caddy.AppDataDir`) και εισαγάγετέ το στον browser ή στο σύστημα ως έμπιστη αρχή.

## Τρέχει ήδη web server σε αυτόν τον υπολογιστή

Αν nginx, Apache ή άλλη ρύθμιση Caddy χρησιμοποιεί ήδη τη θύρα 443 ή 80, το `setup-https.sh` δεν την παίρνει: σταματά και τυπώνει τι να προσθέσετε στον δικό σας server. Για nginx, μέσα στο μπλοκ `server { … }` του https site σας:

```nginx
location / {
    proxy_pass http://127.0.0.1:9014;
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
    proxy_set_header X-Forwarded-For $remote_addr;
    proxy_read_timeout 1d;
}
```

Για Apache (με `mod_proxy`, `mod_proxy_http` και `mod_proxy_wstunnel`):

```apache
ProxyPass        / http://127.0.0.1:9014/ upgrade=websocket
ProxyPassReverse / http://127.0.0.1:9014/
```

Μετά σημειώστε τον σταθμό ως https στο `station.conf`, ώστε το proxy να ανοίξει τη θύρα 9014 και η σελίδα να δείχνει τη διεύθυνση https — ο οδηγός θα πει άλλη μια φορά ότι η θύρα είναι πιασμένη, κάτι αναμενόμενο:

```bash
STATION_HTTPS=y bash configure-station.sh
```

## Αντιμετώπιση προβλημάτων

| Σύμπτωμα | Τι να ελέγξετε |
|---|---|
| `no certificate yet` | Το όνομα DNS πρέπει να δείχνει στη δημόσια διεύθυνσή σας (`ping myname.ddns.net` από έξω από το δίκτυό σας), και το router να προωθεί τις 443 και 80 σε αυτόν τον υπολογιστή. Ο Caddy ξαναδοκιμάζει μόνος του· το log του: `sudo journalctl -u caddy -n 50`. |
| Ο πάροχος κόβει τη θύρα 80 | Ο Caddy αποδεικνύει το όνομα και μόνο μέσω της 443, οπότε στις περισσότερες περιπτώσεις αρκεί η 443· αφήστε την 80 προωθημένη αν μπορείτε. |
| `too many failed authorizations` στο log του Caddy | Το Let's Encrypt επιτρέπει λίγες αποτυχίες την ώρα. Διορθώστε την αιτία, περιμένετε μία ώρα και μετά `sudo systemctl restart caddy`. |
| Το log του Caddy δείχνει `Invalid response … /.well-known/acme-challenge/…` (ένα 502 ή τη σελίδα του δέκτη) ή `Timeout during connect` | Ο router στέλνει την 80 ή την 443 αλλού — συχνά στη δημόσια θύρα του δέκτη. Οι κανόνες πρέπει να είναι TCP 80 → αυτός ο υπολογιστής, θύρα **80**, και TCP 443 → αυτός ο υπολογιστής, θύρα **443**· απενεργοποιήστε την απομακρυσμένη διαχείριση του ίδιου του router σε αυτές τις θύρες. Μετά `sudo systemctl restart caddy` για να ξαναδοκιμάσει αμέσως. |
| Το https λειτουργεί στο σπίτι αλλά όχι απ' έξω | Το router προωθεί την 443 σε άλλον υπολογιστή, ή καθόλου. |
| Η λίστα ακροατών ή το panel χρηστών είναι κενά μέσω https | Τρέξτε μία φορά `bash configure-station.sh` και απαντήστε ναι στη μεταγλώττιση: η σελίδα πρέπει να ξέρει τη διεύθυνση https της. |
| `Port 443 is already used by another web server` | Δείτε παραπάνω το *Τρέχει ήδη web server σε αυτόν τον υπολογιστή*. |
