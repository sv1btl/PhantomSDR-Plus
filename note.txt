WHAT THIS ARCHIVE IS

A file drop over an existing PhantomSDR-Plus installation. Everything in update/ keeps the path it has in the repository, so unpacking it on top of your tree puts each file where it belongs.

Nothing here touches your configuration: no .toml, no site_information.json, no admin_config.json and no frequency list is included, so none of them can be overwritten.

It carries two BACKEND SOURCE files, so the backend has to be rebuilt. The frontend does not.

Almost everything below is KiwiSDR bridge work. If you have never set [kiwi_emulation] enabled = true, the only change that reaches you is manage_admin.sh, and that one needs no rebuild at all.

No new configuration keys. Nothing you have set changes meaning, and there is nothing you must add.


------------------------------------------------------------------------------
 1. HOW TO APPLY
------------------------------------------------------------------------------

  cd ~
  unzip -o update.zip
  cp -a update/. PhantomSDR-Plus/
  cd PhantomSDR-Plus

  ./recompile.sh          # choose [1] Backend only
  ./stop-websdr.sh
  ./start-<your-radio>.sh   # start-rx888mk2.sh, start-airspyhf.sh, start-rsp1a.sh ...

No frontend rebuild, and listeners do not need to reload — nothing they have cached changed.

manage_admin.sh needs no rebuild and no restart of anything: it is only ever read when you run it by hand.


------------------------------------------------------------------------------
 2. WHAT CHANGED
------------------------------------------------------------------------------

A KIWI CLIENT WAS TOLD THE WRONG AUDIO SAMPLE RATE

Read this one first if you run [kiwi_emulation] with audio_sps set to anything other than 12000.

On connecting, the bridge tells a Kiwi client what rate the audio it is about to receive was sampled at. Those two numbers were written into the source as literals — "sample_rate=11998.992747", a figure copied from a real KiwiSDR, and "audio_rate=12000" — while the audio itself was always produced at whatever input.audio_sps says.

At audio_sps = 12000, which is what every shipped config now uses, this was correct by luck and nobody could hear anything wrong. At audio_sps = 192000 — the value config.toml and the HackRF example used to carry — a Kiwi client was told 12 kHz for a stream that was really 192 kHz, and played it at a sixteenth of the proper speed. Unlistenable, and nothing in the client's own settings could have corrected it.

Both fields are now derived from input.audio_sps, so they follow your configuration whatever you set it to. The shipped configs that were on 192000 have been moved to 12000 as well; your own .toml is untouched, as always.


ZOOMING PAST 11 SHOWED DETAIL THAT WAS NOT THERE

Only affects you if you switched on [kiwi_emulation]. Zoomed in far enough, the waterfall and the spectrum a Kiwi client drew stopped showing the real shape of a signal — smooth, plausible, and not the signal.

The reason is architectural, not a coding slip. A real KiwiSDR runs a downconverter and a fresh FFT for each zoom level, so all 1024 values of a waterfall line are genuine at every zoom, right down to 14. PhantomSDR runs ONE FFT across the whole band. At zoom z a client is looking at fft_result_size >> z of our native bins, and that number falls as it zooms in. On a 60 MHz receiver with fft_size = 4194304 it passes below 1024 at zoom 12:

      zoom 11    14.6 kHz     1024 native bins    one real bin per pixel
      zoom 12     7.3 kHz      512 bins           each bin over 2 pixels
      zoom 13     3.7 kHz      256 bins           over 4 pixels
      zoom 14     1.8 kHz      128 bins           over 8 pixels

The previous update taught the bridge to interpolate up to the 1024 values the protocol demands, which cured the BLOCKINESS. What it could not do is invent resolution: past zoom 11 the client was drawing a smooth curve through data that does not exist. Raising fft_size does not rescue a given zoom either — a finer FFT needs fewer native bins to cover the same narrow window, not more.

So the bridge no longer invites it. The zoom_max and zoom_cap it advertises are now computed from your own spectrum width instead of being fixed at 14, and a client simply stops where the last real bin is:

      fft_size = 4194304, 60 MHz real    zoom_max = 11    (14.6 kHz)
      fft_size = 1048576, 8 MHz          zoom_max = 10    ( 3.9 kHz)
      fft_size =  131072, 912 kHz IQ     zoom_max =  7    ( 3.6 kHz)

Note the narrowband receivers reach a lower zoom NUMBER but a finer actual span — zoom is measured against total bandwidth, so that is correct.

If you want a deeper zoom with real data behind it, the lever is input.fft_size: each doubling buys one more level, and the advertised figure follows on its own. It costs FFT work on every frame, so watch your temperatures.

Confirmed on air this time, with AetherSDR: it swept zoom 0 to 11 and never once asked for more. The interpolation stays in place for the spectrum edges and for clients that ignore the advertised limit.


A NOTE ON AUDIO_GAIN, IF YOU HAVE BEEN WINDING IT UP

No change in behaviour here — this is documentation of something that was never written down, in case you have been chasing it.

[kiwi_emulation] audio_gain exists because the bridge sends a Kiwi client exactly the PCM a browser gets, and the browser is loud only because audio.js re-EQs and compresses it afterwards. A look-ahead limiter sits behind the gain so the extra level folds peaks instead of clipping them.

What is not obvious is that it stops working somewhere around 70 dB. Once the limiter is riding continuously it is normalising the envelope to its threshold, so the output settles at threshold divided by the signal's crest factor — about -12 dBFS on speech — no matter what you put in front of it. Measured:

      audio_gain     55      60      66      70      75      80
      output RMS  -17.6   -14.5   -12.8   -12.1   -12.0   -12.0  dBFS

Flat from 70 up. If a Kiwi client still sounds quieter than your web page at 70, the difference is no longer level — it is the browser's EQ and compressor, which have no equivalent on the Kiwi path, and a bigger number will not stand in for them.

The S-meter does not move with audio_gain, at any setting. It is computed from the demodulator's own power figure, which is set before the audio chain ever sees a sample.


THE KIWI DEBUG LOG GREW WITHOUT LIMIT

/tmp/kiwi_retune.log recorded every command a Kiwi client sent that the bridge does not handle. Clients repeat a small handful of those forever — AetherSDR sends a keepalive every few seconds on both sockets, and a maxdb/mindb pair on every drag of its contrast slider. One nine-minute session left 43 kB, and nothing rotates the file.

The repeats carried nothing. The point of that log line is to reveal WHICH commands a client sends that we ignore, and the first sighting says it completely. Only the first occurrence of each distinct command is written now: the same session drops from 277 such lines to 17, and 17 is a ceiling rather than a rate. The periodic S-meter trace thins out after the first few minutes for the same reason.

Nothing you rely on is lost — retunes, zoom changes and frame traces are all still there.


MANAGE_ADMIN.SH REPORTED A RUNNING ADMIN PANEL AS STOPPED

If you run the panel under systemd — the normal setup — then:

      ./manage_admin.sh status

answered "[✗] Admin panel not running" while the panel was up and serving, and had been for weeks. The same for the proxy.

The cause is that the script looked for the panel by one exact spelling of its command line, "python3 /home/you/PhantomSDR-Plus/admin_server.py", which is how the script's own start command writes it. The systemd unit writes it differently — "/usr/bin/python3 -u /home/you/PhantomSDR-Plus/admin_server.py" — so the search never matched anything systemd had started.

Wrong status was the visible half. The dangerous half was start: seeing nothing running, "./manage_admin.sh start" would launch a SECOND panel on top of the one systemd already had on port 3000, and the two would fight over it.

Both spellings are now recognised, and so is any other reasonable one — a different interpreter path, extra flags. The old protection is kept: a command line that merely mentions admin_server.py (an editor with the file open, a diagnostic in another terminal) is still not mistaken for the panel itself.

Nothing about how you start, stop or run the panel changes. If you use systemd, keep using it:

      sudo systemctl restart phantomsdr-admin

If you do not, ./manage_admin.sh start / stop / status work as before — only correctly now.
