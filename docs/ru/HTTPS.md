# Безопасный доступ — https://

Станция PhantomSDR-Plus может быть доступна по **https://**, а не только по http://. Браузер тогда показывает замок, соединение шифруется, и браузеры разрешают странице свой лучший путь для звука (AudioWorklet), в котором они отказывают обычным страницам http. Адрес http продолжает работать в точности как раньше, бок о бок.

Этим занимается **Caddy** — небольшой веб-сервер, который ставится перед приёмником на порт 443. Caddy получает бесплатный сертификат от **Let's Encrypt** для DNS-имени вашей станции и сам обновляет его раз в несколько месяцев, без какого-либо участия с вашей стороны. Если у вас уже есть собственный обратный прокси, который держит сертификат (nginx, Nginx Proxy Manager, Apache, Traefik …), PhantomSDR-Plus работает за ним — см. ниже *Собственный обратный прокси*.

---

## Что нужно

| | |
|---|---|
| **DNS-имя** | Let's Encrypt сертифицирует имена, а не голые IP-адреса. Подойдёт бесплатное имя динамического DNS (no-ip, DuckDNS, dynu и подобные), указывающее на ваш публичный адрес, причём адрес может меняться — имя следует за ним. |
| **Ещё два порта на роутере** | Пробросьте TCP **443** (https) и TCP **80** на компьютер приёмника, вдобавок к вашему публичному порту (9000). Порт 80 нужен только для того, чтобы доказать Let's Encrypt, что имя ваше, при выдаче и обновлении сертификата. |
| **Станция, настроенная с вопросами о станции** | Должен существовать `station.conf`. На станции, установленной до вопросов о станции, сначала один раз выполните `bash configure-station.sh` — он предложит порты, которые ваша станция уже использует, так что ничего не сдвинется. |

## Включение

### При установке

Среди вопросов о станции, в группе **Internet**, выберите **2** в вопросе о https:

```
    1  no https
    2  https through Caddy, set up here: a free Let's Encrypt certificate,
       renewed by itself; needs a DNS name above and ports 443 and 80 open
    3  my own reverse proxy (nginx, Nginx Proxy Manager, Apache, Caddy,
       Traefik …) already serves https:// and forwards to this receiver
  https? [1]: 2
```

Установщик ставит Caddy, получает сертификат и в конце показывает оба адреса.

### На уже работающей станции

```bash
cd ~/PhantomSDR-Plus
bash setup-https.sh
```

Скрипт читает ваше DNS-имя из `station.conf`, устанавливает Caddy (из вашего дистрибутива; в Ubuntu 22.04 — из собственного репозитория Caddy), направляет его на приёмник, пересобирает страницу, чтобы она ссылалась на свой адрес https, перезапускает proxy и ждёт сертификат. Выбор **2** в вопросе о https в `bash configure-station.sh` делает ровно то же самое.

По завершении:

```
  ✔ https://myname.ddns.net/ is live

  https://myname.ddns.net/   — and http://myname.ddns.net:9000/ as before
```

### Проверка и отключение

```bash
bash setup-https.sh --status    # включено ли, и отвечает ли сертификат?
bash setup-https.sh --remove    # отключить https; http остаётся в точности как есть
```

Панель администратора показывает то же в **Настройки → HTTPS**: **🔍 CHECK** на станции с https, а на станции только с http — **🔒 SET UP HTTPS**, которая проверяет, что может, и даёт команды выше для копирования в терминал. См. [Панель администратора](ADMIN_PANEL_SETUP.md).

Если позже сменить DNS-имя через `bash configure-station.sh`, Caddy сам перейдёт на новое имя.

## Как это работает

```
  visitor ──https──► Caddy :443 ──► proxy.py :9014 (this computer only) ──► spectrumserver, panel, RADE …
  visitor ──http───────────────────► proxy.py :9000 ───────────────────────► the same
```

| Порт | Что | Открыт на роутере |
|---|---|---|
| 443 | Caddy — https | да |
| 80 | Caddy — проверка сертификата и перенаправление на https | да |
| 9000 | proxy.py — http, как раньше | да |
| 9014 | proxy.py — сюда Caddy передаёт посетителей | нет — внутри компьютера |

## Что меняется для слушателей

- **Работают оба адреса.** Каталоги и карта websdr.org продолжают показывать адрес http; обратный вызов websdr.org и клиенты Kiwi используют http.
- **Звук лучше через https.** Браузеры дают защищённой странице AudioWorklet — более стабильный путь для звука, чем тот, которым вынуждены пользоваться обычные страницы http.
- **Receive Diversity с партнёрами только на http.** Браузер не позволяет странице https открывать обычные соединения `ws://`, а большинство станций PhantomSDR+ и любой KiwiSDR ничего другого не предлагают. Поэтому со страницы https к ним подключаются через diversity relay станции — см. *Receive Diversity через https* ниже. Партнёры, у которых есть свой https, и UberSDR подключаются напрямую.
- **Управление трансивером (TCI-CAT).** Соединения с `127.0.0.1` на собственном компьютере слушателя разрешены со страницы https в актуальных Chrome, Edge и Firefox. Страница подключается, только когда слушатель открывает **TCI-CAT** или включает **CAT Sync**; тогда Chrome и Edge один раз запрашивают разрешение на доступ к программам и устройствам на компьютере или в сети слушателя. Отказ отключает только TCI-CAT.

## Receive Diversity через https

Страница https подключается к diversity-партнёрам только на http — большинству станций PhantomSDR+, любому KiwiSDR — через собственный relay станции, `websdr_relay.py`, тот же, что обслуживает партнёров WebSDR. Браузер безопасно подключается к `wss://myname.ddns.net/relay/…`, а relay продолжает соединение по `ws://`. Панель делает это сама. Relay передаёт только звук diversity (PhantomSDR+ `/audio`, KiwiSDR `/kiwi/…/SND`), подключается только к публичным адресам и сохраняет свои обычные ограничения. Если он не запущен, страница https подключается только к партнёрам, у которых есть свой https.

Поэтому на станции с https держите relay включённым:

- **Включение https через вопросы станции:** когда https включён, следующий вопрос о relay по умолчанию предлагает «да» — оставьте так, и relay тоже будет установлен и запущен. Сам по себе `bash setup-https.sh` его не устанавливает.
- **Станция, где https уже работает:** проверьте командой `systemctl is-active phantomsdr-websdr-relay`. Если он не активен, запустите `bash setup_websdr_relay.sh` или `bash configure-station.sh` и ответьте «да» на вопрос о relay. За прокси ему не нужен ни порт на роутере, ни пересборка.
- **Проверка:** `https://myname.ddns.net/relay/status` отвечает несколькими строками, начинающимися с `"service": "PhantomSDR-Plus WebSDR relay"`.

Через relay партнёр видит адрес вашей станции, а не слушателя, поэтому партнёр с ограничением на IP считает всех ваших слушателей через relay вместе. Станции только на http ничего этого не нужно: страница http открывает соединения `ws://` и `wss://` напрямую.

## Только в локальной сети — `--lan`

Без DNS-имени https всё равно можно использовать дома:

```bash
bash setup-https.sh --lan
```

Тогда Caddy выпускает собственный сертификат для локального адреса и имени компьютера. Браузеры этот сертификат не знают и в первый раз предупреждают; примите его или сделайте так, чтобы ваши компьютеры доверяли корневому сертификату Caddy:

- на самом компьютере приёмника: `sudo caddy trust`
- на другом компьютере: скопируйте с приёмника `/var/lib/caddy/.local/share/caddy/pki/authorities/local/root.crt` (точный путь показывает `sudo caddy environ`, в `caddy.AppDataDir`) и импортируйте его в браузер или систему как доверенный центр сертификации.

## Собственный обратный прокси

Если у вас уже есть обратный прокси, который отдаёт https:// для ваших доменов — nginx, Nginx Proxy Manager, Apache, Caddy, Traefik, — PhantomSDR-Plus работает за ним, и Caddy не устанавливается. Выберите **3** в вопросе о https:

```bash
bash configure-station.sh        # вопрос о https: 3
```

Затем мастер спрашивает, откуда подключается ваш прокси:

| Ваш прокси работает | Ответ |
|---|---|
| на этом компьютере | `127.0.0.1` |
| на другом компьютере | его адрес, например `192.168.1.20` |
| в Docker на этом компьютере (например, Nginx Proxy Manager) | `172.16.0.0/12` |

Несколько адресов разделяются пробелами. Ответ сохраняется как `STATION_PROXY_FROM` в `station.conf`, рядом с `STATION_HTTPS="external"`, и сохраняется при обновлениях и следующих запусках мастера. Страница тогда ссылается на свой https-адрес, diversity-ретранслятор включён по умолчанию, а мастер заканчивает всем, что нужно вашему прокси. Это можно вывести снова в любой момент:

```bash
bash configure-station.sh --proxy-guide
```

Коротко:

- **Один сайт, один порт.** Перенаправьте `https://vashe.imya/` — целиком — на `http://<этот компьютер>:9014/`. Страница, `/admin`, `/stats`, `/rade`, `/drm` и `/relay` идут через этот один адрес.
- **WebSocket включён.** Звук, водопад и чат — это WebSocket: прокси должен пропускать `Upgrade` и `Connection` и допускать соединения, открытые сутки. В Nginx Proxy Manager отметьте **Websockets Support**.
- **Адрес посетителя** в `X-Forwarded-For` (большинство прокси добавляют его сами). Порт 9014 верит этому заголовку только с указанных вами адресов; любой другой адрес получает **403**, так что никто не может выдать себя за другого.
- **Оставьте внутренними** 9001–9015: никогда не пробрасывайте их на роутере. Пробросьте 443 (и 80, если ваш прокси получает через него сертификат) на ваш прокси и оставьте проброшенным 9000 для http:// — его используют websdr.org, sdr-list и diversity-партнёры только с http.

Для nginx, внутри блока `server { … }` вашего https-сайта (если прокси на другом компьютере, вместо `127.0.0.1` укажите адрес этого компьютера):

```nginx
location / {
    proxy_pass http://127.0.0.1:9014;
    proxy_http_version 1.1;
    proxy_set_header Host $host;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
    proxy_set_header X-Forwarded-For $remote_addr;
    proxy_read_timeout 1d;
}
```

Для Apache 2.4.47 или новее (с `mod_proxy`, `mod_proxy_http` и `mod_proxy_wstunnel`):

```apache
ProxyPass        / http://127.0.0.1:9014/ upgrade=websocket timeout=86400
ProxyPassReverse / http://127.0.0.1:9014/
```

Caddy: `vashe.imya { reverse_proxy 127.0.0.1:9014 }`. Traefik: сервис с URL `http://127.0.0.1:9014`; WebSocket проходит сам.

Затем проверьте с компьютера приёмника:

```bash
bash setup-https.sh --status
```

Проверяется, что порт 9014 слушает, что `https://vashe.imya/` отвечает, что WebSocket проходит через ваш прокси и что в настройках страницы нет http://-адреса станции (https-страница не может его загрузить: mixed content). **🔍 CHECK** в панели администратора показывает то же.

Если `bash setup-https.sh` находит другой веб-сервер на порту 443 или 80, он его не перехватывает: останавливается и отсылает сюда.

## Устранение неполадок

| Признак | Что проверить |
|---|---|
| `no certificate yet` | DNS-имя должно указывать на ваш публичный адрес (`ping myname.ddns.net` из-за пределов вашей сети), а роутер должен пробрасывать 443 и 80 на этот компьютер. Caddy сам продолжает попытки; его журнал: `sudo journalctl -u caddy -n 50`. |
| Провайдер блокирует порт 80 | Caddy умеет доказывать имя и только через порт 443, так что обычно достаточно 443; по возможности оставьте 80 проброшенным. |
| `too many failed authorizations` в журнале Caddy | Let's Encrypt допускает лишь несколько неудач в час. Устраните причину, подождите час, затем `sudo systemctl restart caddy`. |
| В журнале Caddy видно `Invalid response … /.well-known/acme-challenge/…` (502 или страница приёмника) или `Timeout during connect` | Роутер отправляет 80 или 443 не туда — часто на публичный порт приёмника. Правила должны быть такими: TCP 80 → этот компьютер, порт **80**, и TCP 443 → этот компьютер, порт **443**; отключите удалённое управление самого роутера на этих портах. Затем `sudo systemctl restart caddy`, чтобы Caddy сразу попробовал снова. |
| https работает дома, но не снаружи | Роутер пробрасывает 443 на другой компьютер или не пробрасывает вовсе. |
| Список слушателей или панель пользователей пусты через https | Один раз выполните `bash configure-station.sh` и согласитесь на пересборку: страница должна знать свой адрес https. |
| `Port 443 is already used by another web server` | См. выше *Собственный обратный прокси*. |
| За собственным прокси: страница загружается, но нет звука и водопада | Прокси не пропускает WebSocket. nginx: строки `Upgrade` и `Connection`; Nginx Proxy Manager: **Websockets Support**. `bash setup-https.sh --status` это проверяет. |
| За собственным прокси: `forbidden: not the station's https front` | Ваш прокси подключается с адреса, которого нет в `STATION_PROXY_FROM`, — Docker использует свои сети (`172.16.0.0/12`). Запустите `bash configure-station.sh` и добавьте его. |
| За собственным прокси: у всех слушателей один адрес, или четвёртому отказано | Прокси перенаправляет на 9000 вместо 9014 или не отправляет `X-Forwarded-For`. |
